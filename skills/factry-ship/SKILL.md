# Ship a change

Establish the endpoint from the request. Preparing a PR can end with a local draft. Opening a PR ends with a published PR. Merging or enabling auto-merge needs authorization for landing. If “ship” leaves the endpoint ambiguous, inspect and validate locally, then clarify before the ambiguous external action.

1. **Check the destination and scope.** Identify the working repository and branch. For remote delivery, also identify the destination and the intended head and target branches. Inspect staged, unstaged and untracked files. Preserve unrelated work, including changes already staged by the developer. Stage only the requested changes and inspect the resulting commit. Confirm unrelated staged edits are still staged afterward.
   When preparing a PR, publishing or landing, inspect all outgoing commits and the file diff from the merge base. Check each commit's changes where a later revert hides them in the net diff. Before a push, include any additional history it would expose. If the range exceeds the request, preserve the original branch and prepare a scoped branch when authorized, or report which commits need a decision.
2. **Validate the candidate.** Use the repository's documented checks. Run contributor-controlled checks in unprivileged CI or a disposable environment without publishing credentials. Record the commit and which checks ran. If tests ran against a dirty tree, describe that distinction and repeat relevant checks against the committed candidate before claiming they passed there.
3. **Publish when requested.** Compare the candidate with the remote head. Resolve unexpected divergence through the repository's normal workflow. Reuse an existing PR when its head repository, branch and base match. Describe user-visible effects, tests and outstanding gaps. Verify the published head, PR URL, base, and draft or ready state.
4. **Land when requested.** Immediately before merging, enabling auto-merge or entering a queue, refresh the source and target repositories and branches, head SHA, required checks, review decision and merge rules. Reassess a changed head or target. For a required integration check, confirm the provider tested the current combination. Use a merge operation conditioned on the reviewed head. When authorization is limited to a specific destination, verify that the merge operation, queue or repository policy enforces that target through landing. A head check alone permits a same-head retarget. If a required condition cannot be enforced, leave the PR ready and explain the limitation. Follow a queued merge through its actual outcome when landing was requested.

If a push, PR creation or merge returns an ambiguous result, read the remote state before retrying. An open PR, an entry in a merge queue and a completed merge are distinct outcomes. Return the observed endpoint, commit, PR link when applicable, check status and any remaining blocker. For a completed merge, confirm and report the actual target branch and landed commit.
