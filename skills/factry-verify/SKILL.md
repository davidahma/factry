# Verify a change

Start from the developer's original requirements. Independently resolve the applicable development and testing guides, architecture rules and required checks from the trusted target revision or agreed pre-edit state. Cite those sources. Compare any plan or handoff with the request and those rules. Keep omitted requirements and checks in scope. A candidate change to a guide or gate needs its own review. If a governing source is unavailable, name the source you used and the limit on your conclusion.

1. Identify the subject. For a commit or PR, capture the candidate SHA and use a clean checkout or CI evidence for that revision. For a proposed merge, identify the target, both input revisions and the merge SHA actually checked. For local changes, describe relevant staged, unstaged and untracked inputs and attribute observations to that working tree.
2. For each criterion, find the assertion or public observation that could establish it. Derive cases from the contract and the limits introduced by the implementation. For a quantity, inspect the boundaries at parsing, conversion and consumption. A valid value can exceed an internal representation even when ordinary examples pass. For a shared format, exercise supported reader/writer versions. For a retried write, inspect state after loss of confirmation. Choose the cases that can change the verdict. For a wording correction, checking the affected claim or link may be enough. The [test selection guide](references/test-selection.md) gives other examples.
3. Run the relevant checks or inspect their results. Use an isolated environment for contributor-controlled code. Distinguish which checks ran, which code executed and which behavior was asserted. A high coverage percentage can coexist with an unchecked result. Inspect test selection, skips, modified assertions and fixtures even if the check name stays the same. When a changed check could omit a required behavior, exercise it against the candidate with trusted baseline checks or an independent probe. When a test shares an assumption with the implementation, derive an independent expected value or use an independent consumer. Record inputs, expected and observed results, and any required service or permission you lack.
4. Bind each result to the revision and its command or run link. For CI, confirm the expected workflow produced it. For a cache, establish which inputs and revision it covers. If the head or relevant base moves, rerun affected checks or report them against their original subject. A head-only result can still apply while integration with a new base remains unknown.

Give each criterion and required check a verdict of **passed**, **failed**, or **unverified** with its expected and observed result. Record any repo-approved exception and its scope separately from the observed result. A supported counterexample fails the criterion even if several examples pass. If untested cases could change the conclusion, report the observed subset and mark the broader criterion unverified. For a skipped or blocked check, name the smallest step that would close the gap. Report an overall pass only when current evidence supports every applicable requirement and check.
